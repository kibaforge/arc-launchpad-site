ERC-8183: build a USDC escrow job on Arc

Escrow is the highest-value thing you can build on Arc right now. Every grant recipient, freelance marketplace, trade-finance workflow and agent work-market needs conditional settlement, and almost nobody wants to write it twice.

Arc ships two paths to it. Here is when to use which.

Path A — fork Circle's production sample

https://github.com/circlefin/arc-escrow

This is the fastest route to something real. It combines Circle Wallets, the Refund Protocol and the Contract Platform, and includes AI-assisted work validation. If you need escrow this week, start here and read the rest of this page to understand what you are modifying.

Path B — ERC-8183, the onchain job standard

ERC-8183 defines the job lifecycle as a standard: creation, escrow funding, deliverable submission, evaluation, and USDC settlement.

Tutorial: https://docs.arc.io/arc/tutorials/create-your-first-erc-8183-job

Use this when you want the lifecycle to be legible to other contracts — for example an agent marketplace where a third party needs to read job state without calling your API.

The lifecycle

createJob(brief, amount, evaluator)   -> job id, no funds move
fund(jobId)  { value: amount }        -> USDC sits in escrow
submit(jobId, deliverableHash)        -> worker proves delivery
complete(jobId) | refund(jobId)       -> settlement or refund

On Arc, fund is a value-bearing call. Because USDC is the native asset, there is no approve() step and no allowance to manage. That removes an entire class of UX friction — and a whole category of approval-exploit risk.

The client wrapper

import { ethers } from "ethers";

const parseNativeUsdc = (a: string | number): bigint =>
  BigInt(Math.round(Number(a) * 1e6)) * 10n ** 12n;   // 18-decimal native

const FEE = {
  maxFeePerGas: 20n * 10n ** 9n,      // 20 Gwei floor on Arc
  maxPriorityFeePerGas: 1n * 10n ** 9n,
};

async function createAndFund(contract: ethers.Contract, brief: string,
                             amount: string, evaluator: string) {
  const briefHash = ethers.keccak256(ethers.toUtf8Bytes(brief));

  // 1. open the job — cheap, no funds move
  const open = await contract.createJob(briefHash, parseNativeUsdc(amount),
                                        evaluator, FEE);
  await open.wait(1);

  const jobId = /* read from the JobCreated event */;

  // 2. fund the escrow — a value-bearing call, no approve() needed
  const fund = await contract.fund(jobId, { value: parseNativeUsdc(amount), ...FEE });
  await fund.wait(1);

  return jobId;
}

Note wait(1). Arc has sub-second deterministic finality — one confirmation is final. There is no reorg window, so there is no reason to wait for more.

Design decisions that will cost you if you get them wrong

The evaluator is the trust bottleneck. Who decides the deliverable is acceptable? If you hardcode yourself, you have built a custodian, not escrow. Make it pluggable from day one: a multisig, an oracle, or an AI validator with a human appeal path.

Take your fee at funding, not at release. A fee-on-release means the worker receives less than the quoted amount, which breaks their expectation and generates support tickets forever. Take it up front, where it is visible.

Persist the job id against your own record. The chain has the money; your database has the context. Agents crash and restart — the ledger is the only memory that survives.

Handle the no-receipt revert. A transaction to a blocklisted address reverts and consumes gas without a receipt you can point at. Your error path needs a branch that surfaces the tx hash rather than a generic "failed".

Don't promise privacy. Arc Privacy Sector (confidential execution for Solidity contracts) is documented in detail and explicitly marked not yet available. Design for it; do not sell it.
