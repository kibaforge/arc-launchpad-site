Module 1 — Send USDC

On Arc, USDC is the gas token. That changes the transaction you write.

import { ethers } from "ethers";

const provider = new ethers.JsonRpcProvider(RPC_URL);
const wallet   = new ethers.Wallet(process.env.PRIVATE_KEY, provider);

const tx = await wallet.sendTransaction({
  to: recipient,
  value: ethers.parseUnits("1", 6),          // native send, 6-dec interface
  maxFeePerGas: ethers.parseUnits("20", "gwei"), // 20 gwei floor on Arc
});
// Arc finalises in under a second. No confirmation loop needed.
  • 20 Gwei is a floor, not a suggestion. Below it, transactions can sit pending forever or fail outright.
  • Two decimals, one balance. Native accounting is 18 decimals; the ERC-20 interface is 6. Same underlying balance, not two tokens.
  • There is no wrapped USDC. The native asset satisfies IERC20 directly — no WETH-style wrapper to deploy.

Module 2 — Conditional escrow settlement

Fund a job, submit a deliverable, release on verified completion. This is the pattern behind Arc's own escrow sample and the ERC-8183 job standard — it is what you need for freelance payouts, milestone trade finance, and agent work markets.

Module 3 — Agent micropayments (x402)

An agent paying fractions of a cent per API call. This is the use case Arc was explicitly built for, and it is where the ecosystem programme is putting its money.

// Client: agent hits a premium endpoint
const res = await fetch(PAID_ENDPOINT);
if (res.status === 402) {
  // Server quotes a price; agent settles in USDC via Circle Nanopayments
  const quote = await res.json();
  const receipt = await payNanopayment(quote);      // sub-cent, sub-second
  return fetch(PAID_ENDPOINT, { headers: { "X-PAYMENT": receipt } });
}
// Base sample: github.com/circlefin/arc-nanopayments
  • Predictable fees are the whole point. An agent cannot budget against a volatile gas token.
  • Paired with ERC-8004 identity, an agent can hold reputation and get paid autonomously.

Module 4 — Being paid over x402 (the half nobody ships)

Every x402 sample on Arc shows an agent paying. Almost none show how to take the payment. An agent economy where every agent only spends is a subsidy, not an economy — so this module is the seller side, written against how the chain actually behaves.

// Server: quote, then verify the money on-chain before serving anything
const req = quote({ amount: "0.05", payTo: TILL, resource: "/paid/data",
                    description: "One Arc gotcha sheet" });

if (!req.headers["x-payment"])
  return reply(402, challenge(req));          // price, address, nonce, expiry

const verdict = await verifyPayment(req.headers["x-payment"], req);
if (!verdict.ok) return reply(402, { error: verdict.reason });

if (guard.spend(txHash)) return reply(409, { error: "already spent" });
return reply(200, theResource);
  • Decimals handled by the emitting address. 18dp natively, 6dp through the ERC-20 interface, same balance. Get it wrong and you are off by 1012.
  • No confirmation loop. Arc finality is deterministic — one confirmed block is final. Waiting for six is latency on every sale.
  • Rate limits are retried, not refused. The public RPC limits in two shapes, one of which looks exactly like a real refusal.
  • Ten checks against live mainnet, using transactions that really happened. No keys, no funds, all reads.
