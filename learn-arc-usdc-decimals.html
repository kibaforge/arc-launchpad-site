The Arc decimals trap: 18 vs 6, one balance

This is the bug that will cost you the most money on Arc, and it is easy to walk into because the code looks correct.

The situation

On Arc, USDC exists in two interfaces over one underlying balance:

Interface Decimals Address
Native (gas + value transfers) 18 — (it's the native asset)
ERC-20 (optional) 6 0x3600000000000000000000000000000000000000

They are not two tokens. There is no conversion, no bridge, no wrapper. The same USDC sits behind both. What differs is only the decimal scaling you use to talk to it.

Why this is dangerous

Elsewhere in the EVM world, the native asset is ETH at 18 decimals and USDC is a separate ERC-20 at 6. Developers carry that habit over, and then:

// WRONG on Arc — 6 decimals applied to an 18-decimal interface
await wallet.sendTransaction({ to, value: ethers.parseUnits("1", 6) });

That sends 0.000000000001 USDC, not 1 USDC. Off by 10¹². In the other direction you try to send a trillion dollars and the transaction reverts.

Both failures are quiet. The first one just... sends almost nothing, and you find out when a customer says they never got paid.

The fix: one convention per module

Pick a convention, name it in the function, and never convert implicitly.

/** Native interface — 18 decimals. For gas and `value` transfers. */
export const parseNativeUsdc = (amount: string | number): bigint =>
  BigInt(Math.round(Number(amount) * 1e6)) * 10n ** 12n;

/** ERC-20 interface — 6 decimals. For transferFrom / approve / allowance. */
export const parseErc20Usdc = (amount: string | number): bigint =>
  BigInt(Math.round(Number(amount) * 1e6));

/** Format raw native USDC back to a human string. */
export const formatNativeUsdc = (raw: bigint): string =>
  (Number(raw / 10n ** 12n) / 1e6).toString();

Three rules that prevent the whole class of bug:

  1. Name the function after the interface, not after the token. parseNativeUsdc and parseErc20Usdc cannot be confused by someone reading quickly at 2am. parseUsdc can.
  2. Never write a bare 1e6 or 1e18 in business logic. Every literal lives in one config file.
  3. Assert at the boundary. If a value crosses from a native call into an ERC-20 call, check the magnitude. A number that is 10¹² too big is obvious if you look.

Why Arc does this

The native asset needs 18 decimals because it is the gas token and gas accounting is 18-decimal throughout the EVM. The ERC-20 interface stays at 6 because every USDC integration in existence expects 6, and breaking that would break every wallet, indexer and payment processor on the planet.

So Arc keeps both and makes them share a balance. It is the right call. It just means you have to be explicit about which one you are holding.

Related traps

  • There is no wrapped USDC. No WETH-style wrapper to deploy, because the native token already satisfies IERC20. If a tutorial tells you to wrap, it was written for a different chain.
  • The system emitter logs every transfer at 0xffffFFFfFFffffffffffffffFfFFFfffFFFfFFfE. Indexers watching only the ERC-20 address miss native movements.
  • address(0) sends revert. They succeed on most chains. Find your placeholder-address patterns now.
